# 工厂模式

## 工厂模式的作用

1. **封装变化**：对象的创建逻辑有可能发生变化，将创建逻辑封装到工厂类中之后，创建逻辑的变更对调用者透明。
2. **代码复用**：将对象的创建代码抽离到独立的工厂类中，可以在多个地方复用。
3. **隔离复杂性**：封装复杂的对象创建逻辑，调用者无需了解对象是如何创建的。
4. **控制复杂度**：将对象创建代码抽离出来，使原本的函数或类职责更加单一，代码更加简洁。

# 简单工厂

将对象的创建逻辑封装到工厂函数中，调用方不再直接负责创建具体对象，而是通过工厂获取对象。

```go
package main

import "fmt"

type Payment interface {
	Pay(amount float64)
}

type AliPay struct{}

func (a *AliPay) Pay(amount float64) {
	fmt.Printf("支付宝支付：%.2f\n", amount)
}

type WeChatPay struct{}

func (w *WeChatPay) Pay(amount float64) {
	fmt.Printf("微信支付：%.2f\n", amount)
}

// 简单工厂
func NewPayment(payType string) Payment {
	switch payType {
	case "alipay":
		return &AliPay{}
	case "wechat":
		return &WeChatPay{}
	default:
		return nil
	}
}

func main() {
	payment := NewPayment("alipay")
	payment.Pay(100)
}
```

简单工厂将具体对象的创建逻辑集中在 `NewPayment` 函数中，调用者只需要传入对应的类型，就可以获取相应的支付对象，而不需要关心具体创建过程。

不过，简单工厂也有一个问题：当需要创建的产品类型不断增加时，工厂内部的 `switch` 判断也会越来越复杂，每次新增产品都需要修改工厂代码。

# 工厂方法

当创建逻辑不断扩展时，简单工厂本身也可能变得复杂。此时可以利用多态，将具体产品的创建逻辑分散到不同的工厂类中，避免由一个工厂承担所有产品的创建职责，这就是工厂方法模式。

**产品接口及其实现：**

```go
type Payment interface {
	Pay(amount float64)
}

type AliPay struct{}

func (a *AliPay) Pay(amount float64) {
	fmt.Printf("支付宝支付：%.2f\n", amount)
}

type WeChatPay struct{}

func (w *WeChatPay) Pay(amount float64) {
	fmt.Printf("微信支付：%.2f\n", amount)
}
```

**工厂接口及具体工厂：**

```go
type PaymentFactory interface {
	CreatePayment() Payment
}

type AliPayFactory struct{}

func (f AliPayFactory) CreatePayment() Payment {
	return &AliPay{}
}

type WeChatPayFactory struct{}

func (f WeChatPayFactory) CreatePayment() Payment {
	return &WeChatPay{}
}
```

每个具体工厂负责创建对应的产品，不再需要在同一个工厂中判断具体创建哪一种对象。

**定义工厂映射关系：**

```go
var paymentFactories = map[string]PaymentFactory{
	"alipay": AliPayFactory{},
	"wechat":  WeChatPayFactory{},
}

// 获取具体工厂
func GetPaymentFactory(payType string) (PaymentFactory, error) {
	factory, ok := paymentFactories[strings.ToLower(payType)]
	if !ok {
		return nil, fmt.Errorf("unsupported payment type: %s", payType)
	}
	return factory, nil
}
```

这里的 `map` 用于维护支付类型与具体工厂之间的映射关系。它属于额外的工厂选择机制，并不是工厂方法模式本身必须包含的部分。

**客户端调用：**

```go
factory, err := GetPaymentFactory(payType)
if err != nil {
	return err
}

payment := factory.CreatePayment()
payment.Pay(100)
```

客户端通过获取具体工厂来创建产品，不需要直接依赖 `AliPay`、`WeChatPay` 等具体产品的创建逻辑。

### 什么时候应该使用工厂方法模式，而不是简单工厂模式？

当对象的创建逻辑比较复杂，涉及其他对象的初始化和组合时，可以考虑使用工厂方法模式，将不同产品的创建逻辑拆分到各个具体工厂中。

或者当产品类型不断增加，简单工厂中的 `if-else` 或 `switch` 判断过于复杂时，也可以使用工厂方法模式，将创建逻辑分散到不同的工厂中。

不过，工厂方法模式也会引入更多工厂类。如果对象的创建逻辑本身很简单，使用简单工厂可能反而更加直观。

# 抽象工厂模式

抽象工厂模式用来创建**一组具有相互关联或者依赖关系的对象**，将这组对象的创建逻辑封装起来，避免在创建过程中出现产品之间不匹配的问题。

例如，支付系统除了支付功能，还需要退款和通知功能。不同支付渠道可能对应不同的支付、退款和通知实现。如果由客户端分别创建这些对象，就可能出现支付宝支付却使用了微信退款或通知实现的情况。

通过抽象工厂，可以将同一支付渠道下的一组对象统一交给对应工厂创建。

**定义产品接口：**

```go
type Payment interface {
	Pay(amount float64)
}

type Refund interface {
	Refund(amount float64)
}

type Notifier interface {
	Notify(message string)
}
```

**定义抽象工厂接口，负责创建一组产品：**

```go
type PaymentFactory interface {
	CreatePayment() Payment
	CreateRefund() Refund
	CreateNotifier() Notifier
}
```

**实现支付宝工厂：**

```go
type AliPayFactory struct{}

func (f AliPayFactory) CreatePayment() Payment {
	return &AliPay{}
}

func (f AliPayFactory) CreateRefund() Refund {
	return &AliRefund{}
}

func (f AliPayFactory) CreateNotifier() Notifier {
	return &AliNotifier{}
}
```

**实现微信支付工厂：**

```go
type WeChatFactory struct{}

func (f WeChatFactory) CreatePayment() Payment {
	return &WeChatPay{}
}

func (f WeChatFactory) CreateRefund() Refund {
	return &WeChatRefund{}
}

func (f WeChatFactory) CreateNotifier() Notifier {
	return &WeChatNotifier{}
}
```

这里省略具体产品的实现。每个工厂负责创建同一产品族的对象，例如支付宝工厂创建支付宝支付、支付宝退款和支付宝通知对象，微信工厂则创建对应的微信产品。

**客户端调用：**

```go
factory, err := GetPaymentFactory(payType)
if err != nil {
	return err
}

payment := factory.CreatePayment()
refund := factory.CreateRefund()
notifier := factory.CreateNotifier()
```

客户端只需要获取对应的工厂，就可以创建同一产品族中的各个对象，无需关心具体产品的创建过程。

# 依赖注入（DI）容器

依赖注入容器底层的设计思路可以理解为一个大型工厂，通过预先配置好的对象依赖关系来创建并持有对象。

与普通工厂不同，DI 容器不仅负责创建对象，还可以管理对象之间的依赖关系以及对象的生命周期。

## DI 容器的核心功能

1. **配置解析**：解析需要创建的对象及创建对象所需的信息，例如使用哪个构造函数、构造函数需要哪些参数，以及对象之间的依赖关系。
2. **对象创建**：通过反射等机制获取对象的创建方式，并由容器统一负责对象的创建和依赖注入。
3. **对象生命周期管理**：管理对象的生命周期，例如配置单例对象或每次创建新对象、是否采用懒加载，以及对象创建和销毁时的钩子函数。

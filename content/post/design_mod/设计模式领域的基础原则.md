# 面向对象设计原则总结：SOLID、KISS、YAGNI、DRY、迪米特法则
在后端开发、业务系统迭代的过程中，代码质量直接决定后续迭代成本、bug 数量以及团队协作效率。很多同学听过各种设计原则，但容易混淆它们的适用场景、判断标准以及落地方式。本文梳理日常开发中最核心的一套设计原则，配套 Go 代码示例。

## SOLID 五大原则
SOLID 是面向对象编程最经典的五条设计原则，是解耦、提升代码可维护性和扩展性的基础，也是学习设计模式的前置知识。

### 单一职责原则（SRP）
**定义：一个模块或者类只完成一个功能，不要设计大而全的类。**

这里需要特别注意：单一职责不是无限拆分。它是一个灵活的取舍，如果拆分粒度过细，类数量爆炸、调用链路变长，反而会提升理解和维护成本，适得其反。

#### 如何判断一个类职责是否足够单一
可以对照下面几条进行自查：
1. 类内代码行数、方法、属性过多，阅读困难，定位逻辑成本高；
2. 类依赖大量其他外部类，违背高内聚、低耦合的思想；
3. 私有方法数量很多，大量私有逻辑具备独立复用价值，适合抽成新类；
4. 很难用一个清晰的业务名词命名这个类，往往代表内部混杂了多组无关职责；
5. 类中大部分方法都在操作某一小部分属性，可以把这组属性和配套方法抽象为独立类。

❌ 反例：一个结构体同时处理订单计算、持久化、发送消息
```go
package main

import "fmt"

// Order 职责过载：计算金额、保存DB、发通知全部放在一起
type Order struct {
	ID     int
	Amount float64
}

func (o *Order) CalcAmount() float64 {
	return o.Amount * 0.9
}

func (o *Order) SaveToDB() {
	fmt.Println("save order to db")
}

func (o *Order) SendNotify() {
	fmt.Println("send notify to user")
}
```

✅ 优化后，拆分职责
```go
package main

import "fmt"

type Order struct {
	ID     int
	Amount float64
}

func (o *Order) CalcAmount() float64 {
	return o.Amount * 0.9
}

// OrderRepo 只负责存储
type OrderRepo struct{}

func (r *OrderRepo) Save(o *Order) {
	fmt.Println("save order to db")
}

// NotifyService 只负责通知
type NotifyService struct{}

func (n *NotifyService) Send() {
	fmt.Println("send notify to user")
}
```

### 开闭原则（OCP）
**定义：对扩展开放，对修改关闭。新增功能优先通过扩展原有代码实现，而不是修改已有稳定代码。**

在工程实践中，完全不修改旧代码几乎无法做到。这条原则的真实目标，是**让修改尽可能集中、范围更小、尽量落在上层，规避改动核心底层逻辑**。
开闭原则核心目标：提升代码的**可扩展性**。

#### 指导思想
做前期设计时，提前识别系统里**可变部分和不变部分**，为未来可能的变更预留扩展点；将变化的逻辑封装隔离，对外提供稳定、抽象的接口，上层业务只依赖抽象，不感知内部变化。

#### 常用落地手段
多态、依赖注入、基于接口而非实现编程，是落地开闭原则最常用的手段。

❌ 反例：新增折扣类型需要修改原有函数
```go
package main

func GetPrice(typ string, origin float64) float64 {
	if typ == "normal" {
		return origin
	} else if typ == "vip" {
		return origin * 0.8
	}
	// 新增折扣类型必须修改这个函数
	return origin
}
```

✅ 优化后：接口抽象，新增折扣新增实现，不改动原有逻辑
```go
package main

type Discount interface {
	Calc(origin float64) float64
}

type NormalDiscount struct{}
func (d *NormalDiscount) Calc(origin float64) float64 {
	return origin
}

type VipDiscount struct{}
func (d *VipDiscount) Calc(origin float64) float64 {
	return origin * 0.8
}

// 新增折扣只需要新增结构体实现Discount，不需要修改CalcPrice
func CalcPrice(d Discount, origin float64) float64 {
	return d.Calc(origin)
}
```

### 里氏替换原则（LSP）
**定义：子类对象可以替换父类对象，并且替换之后，程序原有逻辑正确性不会被破坏。**

Go 没有继承，依靠接口实现多态，对应理解为：接口的实现类不能违背接口约定。

#### 典型违反场景
1. 实现类违背接口声明承诺要提供的能力；
2. 实现类修改、破坏了接口约定的入参、出参、异常（error）规则；
3. 实现类违背接口注释里写明的特殊约束。

一个简单有效的验证方式：实现类实例可以跑通接口全部单元测试。
简单总结：实现应当用来**拓展能力**，而不是破坏原有约定。

❌ 反例：接口约定返回正常结果，实现类随意返回错误破坏语义
```go
package main

type Shape interface {
	Area() float64
}

type Rectangle struct {
	W, H float64
}
func (r *Rectangle) Area() float64 {
	return r.W * r.H
}

// Square 错误实现，修改入参约束，替换后逻辑异常
type Square struct {
	side float64
}
func (s *Square) Area() float64 {
	if s.side <= 0 {
		return -1 // 违背预期：面积不应该为负数
	}
	return s.side * s.side
}
```

✅ 正确示例：实现遵守接口契约
```go
package main

type Shape interface {
	Area() float64
}

type Rectangle struct {
	W, H float64
}
func (r *Rectangle) Area() float64 {
	return r.W * r.H
}

type Square struct {
	side float64
}
func (s *Square) Area() float64 {
	if s.side <= 0 {
		return 0
	}
	return s.side * s.side
}

// 任意Shape实现都可以安全传入
func PrintArea(s Shape) {
	println(s.Area())
}
```

### 接口隔离原则（ISP）
**定义：接口的使用者（客户端）不应该被强迫依赖自己不需要的接口。**

落实到编码：站在调用方视角，对外暴露的接口，不能携带调用方完全用不到的冗余方法。
不要设计臃肿的大接口，优先拆分出细粒度、职责聚焦的小接口，不同调用方按需依赖。

❌ 反例：大接口，有的实现用不到部分方法
```go
package main

type Animal interface {
	Run()
	Fly()
	Swim()
}

type Dog struct{}
func (d *Dog) Run()  {}
func (d *Dog) Fly()  { panic("dog can not fly") } // 被迫实现不需要的方法
func (d *Dog) Swim() {}
```

✅ 优化：拆分为多个小接口，按需依赖
```go
package main

type Runner interface {
	Run()
}
type Flyer interface {
	Fly()
}
type Swimmer interface {
	Swim()
}

type Dog struct{}
func (d *Dog) Run()  {}
func (d *Dog) Swim() {}

type Bird struct{}
func (b *Bird) Run() {}
func (b *Bird) Fly() {}
```

### 依赖反转原则（DIP）
很多人会把控制反转、依赖注入、依赖反转三者混在一起，这里做清晰区分：

#### 控制反转（IOC）
是一套宏观设计思想：由框架预留扩展点，开发者只在扩展点中编写业务代码，整体流程控制权交给框架，而不是由业务代码手动驱动全流程。

#### 依赖注入（DI）
是实现控制反转的编码技巧：不在类内部使用 `new`（Go里&struct{}）手动创建依赖对象，而是通过构造函数、方法入参等方式，把外部依赖传入结构体使用。

#### 依赖注入框架
把依赖注入的流程自动化。通过配置声明对象、依赖关系，框架自动完成对象创建、生命周期管理、自动注入依赖，解放手动组装对象的重复代码。

#### 依赖反转原则
高层模块不依赖低层模块；高层、低层模块共同依赖抽象。
抽象不依赖具体实现，具体实现依赖抽象。

> 核心一句话：面向抽象编程，而不是面向具体实现编程。

❌ 反例：高层业务直接依赖底层实现
```go
package main

// 底层实现
type MysqlRepo struct{}
func (m *MysqlRepo) Save() {}

// 高层Service 直接依赖Mysql具体结构体
type OrderService struct {
	repo *MysqlRepo
}
func NewOrderService() *OrderService {
	return &OrderService{repo: &MysqlRepo{}}
}
```

✅ 优化：依赖抽象接口
```go
package main

type OrderRepo interface {
	Save()
}

type MysqlRepo struct{}
func (m *MysqlRepo) Save() {}

type RedisRepo struct{}
func (r *RedisRepo) Save() {}

// Service 依赖抽象
type OrderService struct {
	repo OrderRepo
}
// 构造注入
func NewOrderService(repo OrderRepo) *OrderService {
	return &OrderService{repo: repo}
}
```

## KISS 原则 & YAGNI 原则
这两条偏向工程化的务实开发准则，用来对抗“过度设计”。

### KISS 原则
全称：Keep It Short and Simple，保持代码简单。
落地要点：
1. 不引入团队其他成员不熟悉、难以维护的小众技术；
2. 成熟场景优先使用社区轮子，不重复造轮子；
3. 拒绝过早、无收益的过度优化。

示例：简单逻辑不要过度抽象
```go
package main

// KISS：简单校验直接写，没必要套一堆接口
func IsValidAge(age int) bool {
	return age > 0 && age < 120
}
```

### YAGNI 原则
全称：You Ain’t Gonna Need It。
含义：开发阶段，不要为当前不需要的需求做预留设计，不要编写当下用不到的代码。
很多同学会提前预判未来需求，提前写一大堆扩展逻辑，但业务需求经常变更，提前设计的代码最后大概率用不上，白白增加维护负担。

❌ 反例：提前预留一堆暂时不用的方法
```go
package main

type UserService struct{}
func (u *UserService) Get() {}
func (u *UserService) List() {}
func (u *UserService) Archive() {} // 当前版本完全不用
func (u *UserService) Migrate() {} // 当前版本完全不用
```

## DRY 原则
全称：Don’t Repeat Yourself，不要写重复代码。

很多人只看到“复制粘贴相同代码”这一种重复，其实重复分为三类：
1. **实现逻辑重复**：完全一样的代码片段在多处拷贝；
2. **功能语义重复**：两段代码写法不同，但最终对外提供的业务能力完全一致；
3. **执行重复**：同一段逻辑在单次请求链路中被多次重复执行，浪费性能。

> DRY 不是追求“所有代码都必须复用”，而是避免无意义的重复。

❌ 反例：逻辑重复
```go
package main

func CalcUserTax(money float64) float64 {
	return money * 0.03
}
func CalcVipTax(money float64) float64 {
	return money * 0.03
}
```

✅ 优化：抽公共函数
```go
package main

func CalcTax(money float64, rate float64) float64 {
	return money * rate
}
```

## 如何提高代码复用性
复用不是简单抽公共方法，需要配合设计原则一起落地，这里整理可直接落地的方向：
1. 降低代码耦合：强耦合的逻辑很难单独剥离复用；
2. 遵循单一职责：粒度合理、职责单一的单元更容易复用；
3. 模块化：将独立能力封装成模块，以模块为单位复用；
4. 业务逻辑与通用非业务逻辑分离：业务代码和强场景绑定，很难复用；工具、通用能力更容易沉淀；
5. 通用代码下沉：调用方向遵循上层/同层调用下层，下层不反向依赖上层；
6. 合理使用面向对象特性：接口、多态、抽象、封装；
7. 在合适场景下合理使用设计模式。

## 迪米特法则
迪米特法则也叫最小知识原则，经常和高内聚、松耦合配套理解。

### 高内聚、松耦合
- **高内聚**：相关性强、相近的功能放到同一个类，无关功能不要混在一起。单一职责原则是实现高内聚的重要手段；
- **松耦合**：类之间依赖清晰、依赖量少，一个类修改之后，不会连锁引发大量依赖类改动。
高内聚天然有利于实现松耦合。

### 迪米特法则（最小知识原则）
> 每个模块只应该了解那些与它关系密切的模块的有限知识。

两个核心约束：
1. 不存在直接依赖关系的类，不要产生依赖。可以通过分层调用约束、通用抽象约束替代硬编码的专用依赖；
2. 已经存在依赖关系的类之间，尽量只依赖必要的接口。相关能力收敛到同一类，按功能拆分接口，隔离不必要的依赖。

❌ 反例：越级依赖，A 直接访问 C 的内部
```go
package main

type UserInfo struct {
	Addr *Address
}
type Address struct {
	City string
}

func PrintCity(u *UserInfo) {
	println(u.Addr.City) // 直接穿透依赖
}
```

✅ 优化：只和直接朋友通信，封装内部细节
```go
package main

type UserInfo struct {
	addr *Address
}
type Address struct {
	City string
}

func (u *UserInfo) GetCity() string {
	return u.addr.City
}

func PrintCity(u *UserInfo) {
	println(u.GetCity())
}
```

## 写在最后
所有这些原则都不是硬性的、必须100%遵守的铁律，而是权衡取舍的参考标尺。没有万能最优方案，编码时需要结合业务复杂度、迭代节奏、团队规模综合判断。
它们共同的目标一致：写出更容易读懂、更容易修改、改出bug更少的代码。

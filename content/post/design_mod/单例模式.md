# 单例模式

单例模式的朴素定义：一个类只允许创建一个对象或者实例，这个类就叫做单例类，这种模式就叫做单例模式。

# 为什么要使用单例

1. 避免重复创建，节省资源：对于创建成本较高、生命周期较长的对象，避免重复初始化与资源浪费。
2. 避免重复创建，节省资源：对于创建成本较高、生命周期较长的对象，避免重复初始化与资源浪费。
3. 保证共享状态的一致性：多个调用方使用同一个对象，避免各自维护状态造成不一致。

# 如何实现单例类

要实现一个单例，主要注意以下几个关键点：

1. 限制实例创建入口：避免外部随意创建实例。
2. 并发安全：多个线程或 Goroutine 同时获取实例时，确保不会创建多个实例。
3. 初始化时机：是程序启动时创建，还是首次使用时创建（是否支持延迟加载）。
4. 访问入口的同步机制：是否需要加锁，以及如何减少锁带来的性能开销。

## 饿汉式

在类加载的时候就创建好 `instance` 实例，这种方式不支持延迟加载，会提前占用一定的内存资源。

Go 语言没有 Java 中的类加载机制，但可以通过包初始化机制实现类似的效果。包级变量在包初始化阶段完成初始化，且初始化过程由 Go 运行时保证顺序和安全性。

- 包变量在包初始化阶段完成初始化。
- 包初始化在程序运行过程中只执行一次。
- 包初始化完成后，其他 Goroutine 才能正常使用该包。
- 初始化完成后，如果只是并发读取 `instance`，不存在并发读写问题。

```go
package singleton

type Singleton struct{}

var instance = &Singleton{} // 包初始化时创建实例

func GetInstance() *Singleton {
	return instance
}
```

## 懒汉式

懒汉式是在需要使用实例时才创建对象，避免程序启动时就创建实例。需要考虑并发场景下多个 Goroutine 同时调用 `GetInstance` 时，可能重复创建对象的问题。

### 通过互斥锁保证线程安全

通过双重检查锁（Double-Checked Locking，DCL）实现懒加载。先无锁判断实例是否已经创建，只有实例尚未创建时才加锁，减少加锁次数。

```go
package singleton

import (
	"sync"
	"sync/atomic"
)

type Singleton struct{}

var (
	instance atomic.Value // 使用 atomic.Value 保证并发读写安全
	onceDCL  sync.Mutex
)

func GetInstanceDCL() *Singleton {
	// 第一次检查：无锁快速路径
	if v := instance.Load(); v != nil {
		return v.(*Singleton)
	}

	onceDCL.Lock()
	defer onceDCL.Unlock()

	// 第二次检查：加锁后再次确认
	if v := instance.Load(); v != nil {
		return v.(*Singleton)
	}

	s := &Singleton{}
	instance.Store(s)
	return s
}
```

这里使用 `atomic.Value` 保证实例的并发读写安全。第一次检查时，如果实例已经创建，就直接返回；如果还没有创建，则进入锁保护区域，并再次检查实例是否已经被其他 Goroutine 创建，避免重复初始化。

### 使用 sync.Once 简化

本质上也是通过同步机制保证只初始化一次，只不过使用了 Go 封装好的 `sync.Once`，实现更加简单。

```go
package singleton

import "sync"

type Singleton struct{}

var (
	instance *Singleton
	once     sync.Once
)

func GetInstanceOnce() *Singleton {
	once.Do(func() {
		instance = &Singleton{}
	})
	return instance
}
```

`sync.Once` 保证传入的函数只会执行一次，即使多个 Goroutine 并发调用 `GetInstanceOnce`，也只有一个 Goroutine 会执行实例初始化逻辑。

# 单例模式存在什么问题

单例的使用方式有些类似于硬编码，会带来很多问题。

1. 单例对 OOP 特性的支持不友好，它的使用方式更多是基于具体实现，而非基于接口，容易导致代码耦合。
2. 单例会隐藏类之间的依赖关系，实例创建过程被封装起来，调用方不容易感知依赖。
3. 单例对代码的拓展性不友好，如果需要在代码中创建两个或者多个实例，就可能需要大幅改动代码。
4. 单例对代码可测试性不友好，难以 Mock，同时它所持有的成员变量类似于全局变量，容易导致测试之间相互影响。
5. 单例不支持有参数的构造函数，或者说不方便支持不同参数创建不同实例。如果需要根据不同参数创建实例，通常需要改造成工厂模式或者多例模式。

# 如何设计一个集群环境下的分布式单例模式

## 如何理解单例模式中的唯一性

单例模式中的唯一性需要明确作用范围。通常我们所说的单例，是指在一个进程空间中只有一个对象实例，也就是进程内唯一。

如果将单例的范围扩展到多个进程甚至多个机器，就需要借助外部机制来保证唯一性，例如文件锁、分布式锁等。

## 每个协程唯一的单例

如果单例的作用范围不是整个进程，而是每个 Goroutine 都拥有一个独立的实例，那么就不属于传统意义上的单例模式，而是每个 Goroutine 独立维护自己的对象。

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type IDGenerator struct {
	id atomic.Int64
}

func (g *IDGenerator) GetID() int64 {
	return g.id.Add(1)
}

func NewIDGenerator() *IDGenerator {
	return &IDGenerator{}
}

func worker(wg *sync.WaitGroup) {
	defer wg.Done()

	// 每个 Goroutine 初始化自己的 Generator
	generator := NewIDGenerator()

	fmt.Println(generator.GetID()) // 1
	fmt.Println(generator.GetID()) // 2
	fmt.Println(generator.GetID()) // 3
}

func main() {
	var wg sync.WaitGroup

	for i := 0; i < 3; i++ {
		wg.Add(1)
		go worker(&wg)
	}

	wg.Wait()
}
```

这里每个 Goroutine 都会创建自己的 `IDGenerator`，各自维护独立的 ID 计数器，互不影响。

## 集群唯一的单例

如果需要将唯一性扩展到多个进程，就需要借助外部存储或者协调机制来保证实例的唯一性。

例如，可以通过文件锁实现进程间互斥，同时将对象状态序列化后保存到文件中。下面的例子通过文件锁保证同一时间只有一个进程能够获取实例，并通过文件实现状态持久化。

```go
package singleton

import (
	"encoding/json"
	"os"
	"sync"
	"syscall"
)

type Singleton struct {
	Count int64
}

var (
	instance *Singleton
	mu      sync.Mutex // 进程内互斥
	lockFile *os.File
	dataFile = "/tmp/singleton.json"
)

func GetInstance() (*Singleton, error) {
	mu.Lock()

	if instance != nil {
		return instance, nil
	}

	// 获取进程间锁
	f, err := os.OpenFile(dataFile+".lock", os.O_CREATE|os.O_RDWR, 0644)
	if err != nil {
		mu.Unlock()
		return nil, err
	}

	if err := syscall.Flock(int(f.Fd()), syscall.LOCK_EX); err != nil {
		f.Close()
		mu.Unlock()
		return nil, err
	}

	// 从文件恢复实例状态
	instance = &Singleton{}
	data, err := os.ReadFile(dataFile)
	if err == nil {
		_ = json.Unmarshal(data, instance)
	}

	lockFile = f
	return instance, nil
}

func FreeInstance() error {
	if instance == nil {
		mu.Unlock()
		return nil
	}

	// 持久化实例状态
	data, err := json.Marshal(instance)
	if err == nil {
		err = os.WriteFile(dataFile, data, 0644)
	}

	instance = nil

	// 释放进程间锁
	_ = syscall.Flock(int(lockFile.Fd()), syscall.LOCK_UN)
	_ = lockFile.Close()
	lockFile = nil

	mu.Unlock()
	return err
}
```

这里通过文件锁实现进程间互斥，避免多个进程同时获取实例并修改共享状态。

需要注意，这种方式更接近于通过文件锁实现跨进程的共享状态访问和持久化，并不是真正意义上的分布式单例。文件锁主要适用于共享同一文件系统的进程，如果扩展到多个机器，通常需要借助 Redis、ZooKeeper 等分布式协调机制。

另外，文件锁的生命周期、异常退出后的锁释放、持久化过程中的并发读写以及数据损坏等问题，都需要在实际使用时进一步考虑。

## 多例模式

多例模式根据指定的标识维护对象实例，确保相同标识获取到同一个实例，而不同标识可以对应不同实例。

例如，可以根据 Logger 的名称维护多个日志实例，不同业务使用不同的 Logger，相同名称则共享同一个 Logger。

```go
package logger

import "sync"

type Logger struct {
	name string
}

var instances sync.Map // map[string]*Logger

func GetInstance(loggerName string) *Logger {
	if v, ok := instances.Load(loggerName); ok {
		return v.(*Logger)
	}

	l := &Logger{name: loggerName}
	actual, _ := instances.LoadOrStore(loggerName, l)

	return actual.(*Logger)
}

func (l *Logger) Log() {
	l1 := GetInstance("User")
	l2 := GetInstance("User")  // 和 l1 获取到的是同一个实例
	l3 := GetInstance("Order") // 和 l1 是不同的实例
}
```

这里通过 `sync.Map` 保存不同名称对应的 Logger 实例，使用 `LoadOrStore` 保证并发场景下同一个名称只会保存一个实例。即使多个 Goroutine 同时创建同一个 Logger，也会返回最终存储在 Map 中的实例。
